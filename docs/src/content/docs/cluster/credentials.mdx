In a cluster, Turf™ reads credentials by the same rule as on a laptop: each process reads its own (see
[Where credentials are read](/docs/environment/where-credentials-are-read/)). In a cluster, that rule
decides which pod each Secret goes on:

- **Provider credentials go on the engine.** Provider plugins run there.
- **State backend credentials and `TF_VAR_` go on the server.** The server reads and writes state and
  evaluates variables.
- **The CLI configuration goes on both**, one ConfigMap, since both install providers from it.
- **The identity key is split.** restate-server holds the private half, the engine the public half.

## Providers: the engine

Provider plugins run in the engine, so the environment they see is the engine pod's, never the
server's. Put their credentials in a Secret and give it to the engine's container with `envFrom`:

```sh
kubectl -n turf create secret generic turf-provider-credentials \
  --from-literal=ARM_CLIENT_ID=... --from-literal=ARM_CLIENT_SECRET=... \
  --from-literal=ARM_TENANT_ID=... --from-literal=ARM_SUBSCRIPTION_ID=...
```

```yaml
# The engine's container
envFrom:
  - secretRef:
      name: turf-provider-credentials
```

The usual names apply: AWS `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`; Azure
`ARM_SUBSCRIPTION_ID`, `ARM_CLIENT_ID`, `ARM_CLIENT_SECRET`, `ARM_TENANT_ID`; GCP
`GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_PROJECT`. With the credentials in the environment, a default
provider instance needs no block at all. Provider arguments in the HCL (`profile`, `assume_role`,
`config_path`) override the environment.

A kubernetes or helm provider configured in-cluster authenticates as the **engine's ServiceAccount**.
What that ServiceAccount may do is what an approved plan may do, so grant exactly what your
configurations declare. The example configuration creates a namespace and a ConfigMap in it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: turf-engine
rules:
  - apiGroups: [""]
    resources: [namespaces, configmaps]
    verbs: [get, list, watch, create, update, patch, delete]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: turf-engine
subjects:
  - kind: ServiceAccount
    name: turf-engine
    namespace: turf
roleRef:
  kind: ClusterRole
  name: turf-engine
  apiGroup: rbac.authorization.k8s.io
```

From turf-kagent's `engine.yaml`. A configuration that manages more needs more: widen the ClusterRole
to what it declares, or, for a cluster the agent runs entirely, bind `cluster-admin`.

## The state backend and variables: the server

The server never runs a provider. It opens state and evaluates variables, from its own environment:

- **The Kubernetes® backend** authenticates as the server's ServiceAccount, with
  `in_cluster_config: true` in `open`'s `backend_config`. State is a Secret,
  `tfstate-<workspace>-<suffix>`, and the lock a Lease, `lock-tfstate-<workspace>-<suffix>`, in the
  namespace `backend_config` names:

  ```text
  open({
    workspace_name: "demo",
    backend_type:   "kubernetes",
    backend_config: { secret_suffix: "turf", namespace: "turf", in_cluster_config: true }
  })
  ```

  The server's Role needs Secrets and Leases in that namespace, and nothing else
  ([Minimal manifests](/docs/cluster/manifests/#the-mcp-server)).
- **Any other backend** (S3, azurerm, gcs, `remote`) reads its credentials from the server's
  environment, plus `open`'s `backend_config`.
- **`TF_VAR_<name>`** comes from the server's environment. `open`'s `var` and `var_file` are kept per
  workspace in the server's memory only: after the server restarts, `open` the workspace again with
  the same values.
- **State encryption**: `TF_ENCRYPTION` and a key provider's own credentials come from the server's
  environment.

```yaml
# The server's container: backend credentials, TF_VAR_ values, TF_ENCRYPTION
envFrom:
  - secretRef:
      name: turf-server-env
```

Kubernetes RBAC cannot scope `create` and `list` on Secrets by name, so the server can read every
Secret in the namespace that holds state. If the engine's identity key and the server's own token are
in that namespace, it can read them too. To narrow it, keep state in a namespace of its own (the
`namespace` in `backend_config`) and move the Role there.

## The CLI configuration

The OpenTofu™ CLI configuration's `provider_installation` block says where provider plugins come from
<Since v="1.2" />. The server's `init` installs and locks providers from it, and the engine installs
from it when it plans and checks what `init` locked, so both must read the same block. Use one
ConfigMap, mounted on both and named by `TF_CLI_CONFIG_FILE`. For a cluster that reaches no registry,
add a mirror, name what it serves with `include`, and exclude the same from `direct`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: turf-cli-config
  namespace: turf
data:
  turf.tfrc: |
    provider_installation {
      # filesystem_mirror {
      #   path    = "/turf/providers"
      #   include = ["registry.opentofu.org/hashicorp/*"]
      # }
      # network_mirror {
      #   url     = "https://providers.example.internal/"
      #   include = ["registry.opentofu.org/hashicorp/*"]
      # }

      # With a mirror above: direct { exclude = ["registry.opentofu.org/hashicorp/*"] }
      direct {}
    }
```

- **`filesystem_mirror`**: a read-only volume at the same absolute path in every pod, such as an image
  volume holding what `tofu providers mirror -platform=linux_amd64 -platform=linux_arm64` writes.
- **`network_mirror`**: an https service; tofu refuses http.
- **`oci_mirror`**: an OCI registry, with its credentials in a Docker-style config mounted from a
  Secret at `~/.docker/config.json` (`/home/turf` in the image).

Each pod reads the file once, at start: restart every pod that mounts it after a change. A file in
error stops the pods from starting, where tofu would warn and carry on.

**Registry tokens stay out of the ConfigMap.** A token for a private registry, a mirror host or the
`remote` backend is `TF_TOKEN_<host>` (dots as underscores), from a Secret, on every pod: the server
needs it for the `remote` backend and `init`'s installs, the engine for the installs a plan makes.

## The identity key: restate-server and the engine

restate-server signs every request it sends the engine, and the engine serves nothing it did not sign
(one path, `/health`, answers unsigned). The key pair lives in one Secret, `turf-engine-identity`:

| Half | Goes to | As |
|---|---|---|
| `identity.pem`, private | restate-server | `RESTATE_WORKER__INVOKER__REQUEST_IDENTITY_PRIVATE_KEY_PEM_FILE`, or a `RestateCluster`'s `security.requestSigningPrivateKey` |
| `public-key`, public | the engine | `TURF_ENGINE_IDENTITY_KEYS` (comma-separated, for more than one restate-server) |

Mount only the private half on restate-server. `turf-engine --identity-keygen` makes the pair
([Minimal manifests](/docs/cluster/manifests/#the-namespace-and-secrets)). The engine's
`--insecure-no-identity` turns the check off: anything that can reach the engine's port can then run
any engine handler on input of its choosing, with the engine's credentials. Leave it off.

## RBAC at a glance

| ServiceAccount | Needs | And nothing else because |
|---|---|---|
| `turf-mcp-server` | Secrets and Leases in the state namespace, for the Kubernetes backend | it never runs a provider |
| `turf-engine` | what its providers manage | an approved plan can do what the engine can |
| the console | nothing (`automountServiceAccountToken: false`) | it reads restate-server's ingress alone |

Workload identity tokens that Turf mints for each round's providers, in place of a static key in a
Secret, are coming soon <Since soon />: see [Workload identity](/docs/environment/workload-identity/).
