Any client that speaks MCP over HTTP can drive Turf™ in a cluster. It connects to the server's `/mcp`
endpoint and sends one header with every request:

```text
Authorization: Bearer <token>
```

The token is the one in the `turf-mcp-auth` Secret, which the server reads as `TURF_MCP_AUTH_TOKEN`
. A request without it gets `401`. An agent in the cluster connects to the Service,
Claude Code on your laptop through a port-forward, a CI job like any other client.

## Check the endpoint

Through a port-forward, without the token:

```sh
kubectl port-forward -n turf svc/turf-mcp-server 3000
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:3000/mcp   # 401
```

Read the token out of its Secret when a client needs it:

```sh
kubectl -n turf get secret turf-mcp-auth -o jsonpath='{.data.token}' | base64 -d
```

## Claude Code, through a port-forward

Forward the server's port, then register it with Claude Code over HTTP, the header included:

```sh
kubectl port-forward -n turf svc/turf-mcp-server 3000
```

```sh
claude mcp add --transport http turf http://localhost:3000/mcp \
  --header "Authorization: Bearer $(kubectl -n turf get secret turf-mcp-auth -o jsonpath='{.data.token}' | base64 -d)"
```

A port-forward reaches the pod through the API server, past the cluster's network plugin, so the
server's NetworkPolicy need not admit you: the token is what you show. Paths you name to `init` are
paths in the server's pod, such as `/turf/config`, not on your laptop. With `TURF_CONSOLE_URL` set to
`http://localhost:8873` on the server and the console forwarded too, the `console_url` in every result
opens in your browser ([The console in a cluster](/docs/cluster/console/)).

## An agent in the cluster

An agent's pod connects to the Service, `http://turf-mcp-server.turf.svc.cluster.local:3000/mcp`, with
the header, and the server's NetworkPolicy admits its pods
([Minimal manifests](/docs/cluster/manifests/#the-mcp-server)). How the agent gets the header is its
runtime's business. kagent sends it from a Secret named in a `RemoteMCPServer`'s `headersFrom`, and the
agent's own sandbox never holds it: see [An agent in the cluster, with
kagent](/docs/cluster/example-kagent/).

## A CI job

A CI job is one more client: the same endpoint and the same header, with the token from the CI
system's secrets. Two server flags shape what such a client gets:

- **`--tier`** (`read`, `plan`, `apply` or `full`) decides which tools a server lists
  and what their arguments may do. A credential handed to a server buys its tier's calls and no other.
  At `plan`, every run is `plan_only` and ends `planned`, with a planfile for an applier. To give one
  client less than another, run a server per tier, each with its own token.
- **`--deadline`** is how long a convergence call may run before it returns the stage
  the convergence has reached, with `ended: false` and `next` naming the call that follows, while the
  convergence goes on in the engine. The default, 55 seconds, sits under the MCP TypeScript SDK's
  60-second request timeout. A client with a shorter call timeout needs a shorter deadline: kagent
  gives a call 30 seconds, so the kagent example runs the server with `--deadline=25s`.

## The Turf CLI on a laptop

`TURF_RESTATE_URL` points the Turf CLI (or a server on your laptop) at an engine running elsewhere,
such as in a cluster, instead of the local service. The server then runs on your laptop and the engine
in the cluster, which settles three things:

- **The configuration.** The engine reads each configuration itself, so it must find it: at the same
  path the server names, or below `turf-engine --workdir`, with the server's `--workdir` set to the
  directory holding the same layout.
- **Credentials.** The state backend's credentials and `TF_VAR_` come from your laptop's environment,
  where the server runs. Providers still run in the engine, with the engine pod's credentials.
- **Versions.** The Turf CLI and `turf-mcp-server` must be the same release.

<Aside type="caution">
restate-server's ingress has no authentication of its own. The manifests in this chapter admit only
the server and the console to it, so they give a laptop no way in.
</Aside>

## At a glance

| Client | Connects to | Shows |
|---|---|---|
| An agent in the cluster | the Service, `turf-mcp-server.turf.svc:3000/mcp` | the bearer token, from a Secret |
| Claude Code on a laptop | `localhost:3000/mcp`, through `kubectl port-forward` | the bearer token, in `--header` |
| A CI job | the server's endpoint | the bearer token, from the CI system's secrets |
| The Turf CLI | restate-server's ingress, `TURF_RESTATE_URL` | nothing: the ingress has no authentication |
