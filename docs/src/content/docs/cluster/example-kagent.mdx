kagent is one way to put an agent beside Turf™: the agent runs in the cluster and reaches Turf's MCP
server over HTTP, like any other client. The [turf-kagent](https://github.com/turfbuild/turf-kagent)
repository builds the whole setup on a kind cluster: one step makes the engine's AWS key, and one script
does the rest. The cluster is the control plane,
and what the agent runs is outside it: a fleet of AWS Lambda functions, which it calls after each
rollout to check that the fleet answers.

kagent 1.0 runs the agent in a gVisor sandbox. The engine runs as a Knative service on restate-server,
scaling from zero when a round starts and back to zero after. It holds the AWS key, and the agent's
sandbox holds no credential. State stays in the cluster, a Secret per stack. Every apply waits for a
person in the kagent UI.

<KagentFigure caption="<b>What runs where.</b> A person asks and approves in the kagent UI. The agent plans through Turf's MCP server. The engine applies, with the AWS key, and the agent then fetches the public URLs of what it built." />

Turf's side is the [minimal set](/docs/cluster/manifests/) in its operator and Knative form, in the
`turf` namespace, with an AWS key on the engine and state in a namespace of its own. The rest is
kagent's. [What runs where](#what-runs-where) lists every namespace, and
[Agentic IaC for Platform Teams](https://turf.build/reference-architectures/agentic-iac-for-platform-teams/)
is the paper that walks one run of this example.

## Before you start

You need Docker, [kind](https://kind.sigs.k8s.io) v0.32 or later, kubectl, Helm® 3 or later, the
kagent CLI 1.0.0, an Anthropic API key and an AWS account. kagent 1.0 needs Kubernetes® 1.37.

## Set it up

<Steps>

1. Install the kagent CLI:

   ```sh
   curl -fsSL https://raw.githubusercontent.com/kagent-dev/kagent/refs/heads/main/scripts/get-kagent \
     | bash -s -- --version v1.0.0
   ```

2. From a clone of turf-kagent, make the engine's AWS key with your own AWS session:

   ```sh
   git clone https://github.com/turfbuild/turf-kagent && cd turf-kagent
   turf -C setup/aws up        # or: tofu -chdir=setup/aws init && tofu -chdir=setup/aws apply
   ```

3. Create a kind cluster and run the setup:

   ```sh
   kind create cluster --name turf-kagent --image kindest/node:v1.37.0
   export ANTHROPIC_API_KEY=...
   ./setup/up.sh
   ```

</Steps>

`setup/aws` creates an IAM user, `turf-kagent-engine`, with one policy and one access key, and writes
the key to `.secrets/`, which git ignores. The policy covers Lambda functions in one region and IAM
roles, both only under names that start with `turf-kagent-`, and nothing else in the account.

`setup/up.sh` runs four setup scripts in order: Knative Serving with Kourier, the Restate operator,
kagent, and the Secrets. Then it applies `manifests/turf` and `manifests/kagent` and waits for the
agent. Every step is safe to run again. It refuses a kubectl context that is not a kind cluster unless
you set `FORCE=1`.

## How the agent reaches Turf

kagent lists Turf's tools from a `RemoteMCPServer`. The bearer token comes from a Secret named in
`headersFrom`:

```yaml
apiVersion: api.kagent.dev/v1alpha3
kind: RemoteMCPServer
metadata:
  name: turf
  namespace: kagent
spec:
  url: http://turf-mcp-server.turf.svc.cluster.local:3000/mcp
  protocol: STREAMABLE_HTTP
  # A call gets five minutes, and the server answers within its --deadline (4m). Both are long so
  # that an apply in AWS ends inside one call: kagent asks for approval on every apply call.
  timeout: 5m0s
  sseReadTimeout: 10m0s
  headersFrom:
    - name: Authorization
      valueFrom:
        type: Secret
        name: turf-mcp-auth
        key: authorization
```

The `turf-mcp-auth` Secret in the `kagent` namespace holds the whole header value, `Bearer ` included,
and kagent sends it as it is. kagent's controller reads the Secret to list the tools. The agent never
holds it: its sandbox sends a placeholder, and Agent Substrate's egress gateway puts the real value in
on the way out. The Anthropic key travels the same way. The server's NetworkPolicy admits only kagent's
controller and the egress gateway.

## What the agent runs, and who holds what

The configuration comes from the examples image, `ghcr.io/turfbuild/turf-examples:1.0.0`: the
[turf-examples](https://github.com/turfbuild/turf-examples) repository, mounted read-only at
`/turf/examples` in the server's pod and every engine pod. The agent gives Turf a path inside it,
[`terraform/aws/lambda-fleet`](https://github.com/turfbuild/turf-examples/tree/main/terraform/aws/lambda-fleet):
one execution role, a fleet of Lambda functions, a public URL for each, and a turf action that verifies
the rollout. The agent operates the configuration and does not edit it. A change is a new image version.

- **The engine holds the AWS key**, in the `turf-aws` Secret that only its pods mount. Its
  ServiceAccount is bound to no Role, so it changes nothing in the cluster it runs in.
- **The agent holds no cloud credential**, and it has no Kubernetes tools to fetch one with. kagent's
  built-in tool server runs as `cluster-admin`, so this agent does not bind it.
- **State has a namespace of its own**, `kagent-tfstate`: a Secret and a Lease per stack. The server's
  Role covers that namespace and nothing else, so the server cannot read the Secrets in `turf`.
- **The sandbox's egress is denied by default.** The egress gateway allows the model and the Agent's
  MCP servers because they are named. An `EgressPolicy` that the Agent selects adds one more origin,
  `https://*.lambda-url.us-west-2.on.aws`: the public URLs of Lambda functions in one region. The AWS
  API is not on the list.

## Approvals

The agent's tools come in three bindings:

- Turf's calls that change nothing on their own: `init`, `open`, `up`, `destroy`, `plan`, `show` and
  the rest. They run freely. They can start a round and plan it, and the round then waits at its
  approval point.
- Turf's four calls that change infrastructure or state, `apply`, `taint`, `untaint` and `delete`,
  bound with `requireApproval: true`.
- The OpenTofu® Registry's documentation tools, each named.

Each of the four pauses the agent until a person approves it in the kagent UI. `apply` carries the
digest of the plan it applies, so the approval covers exactly that plan. kagent's approval request
shows only the call's arguments: the convergence and the digest. The agent's prompt has it call `show`
right before `apply`, so the plan is the result just above the request. It is also the round's Plan tab
in the console. Reject with a reason and nothing is applied: the reason reaches the agent, which
cancels the convergence, freeing the stack's lock, and asks what you want instead.

The configuration also declares a turf action, `verify`: a step of the apply that the agent carries out
instead of a provider. After the fleet is created or patched, the apply pauses, and the agent fetches
every function's URL from its sandbox and checks that each answers with the declared greeting. It
reports the result through `apply` again, so kagent asks for a second approval.

## Run it

In one terminal, watch the engine. It sits at zero:

```sh
kubectl get pods -n turf -l app=turf-engine -w
```

In two more, forward the kagent UI and the Turf console:

```sh
kubectl port-forward -n kagent svc/kagent-ui 8082:8080      # http://localhost:8082
kubectl port-forward -n turf svc/turf-console 8873
```

Pick the agent `turf` in the kagent UI, and sign in to the console once with its token:

```sh
open "http://localhost:8873/login?token=$(cat .secrets/console-token)"
```

Then ask the agent:

1. **"Deploy the Lambda fleet as a stack called demo."** The agent loads Turf's deployment skill, runs
   `init` on `/turf/examples/terraform/aws/lambda-fleet`, opens workspace `demo` on the kubernetes
   backend, starts `up` with the stack's variables (two functions, `turf-kagent-demo-0` and
   `turf-kagent-demo-1`), plans, and stops at the approval point. Engine pods appear in the first
   terminal as soon as it opens the workspace. kagent asks you to approve `apply`. The plan is 9 to
   add: the execution role and its policy attachment, two functions, a URL and a permission for each,
   and the rollout marker. Approve, and the apply pauses at the turf action: the agent fetches both
   URLs and reports back through `apply`. Approve that too. The engine pods go away a minute or so
   after the round ends, and the functions answer anyone:

   ```sh
   curl https://<id>.lambda-url.us-west-2.on.aws/
   # {"message":"Hello from the cluster.","function":"turf-kagent-demo-0"}
   ```
2. **"Change demo's greeting to 'Patched from the cluster.'"** A second plan: two updates in place and
   the rollout marker. You approve it, the agent fetches both URLs again and reports the new greeting,
   and you approve that report.
3. **"What is in demo?"** Read-only, no pause. The agent reads the stack's state through Turf. Ask it
   for the AWS key, or any Secret, and it cannot get one. To see every stack yourself, run
   `kubectl get leases -n kagent-tfstate`: there is one Lease per stack.
4. **"Tear down the demo stack."** kagent asks for approval again, this time for a destroy plan. Reject
   it with a reason and nothing is applied. Ask again and approve, and the fleet is gone.

Restate's UI shows each round's invocations: `kubectl port-forward -n turf svc/restate 9070`, then
`http://localhost:9070`.

## Other clients

The agent is an A2A endpoint on kagent's controller, so anything that speaks A2A can drive it. To
answer an approval, a client requests the extension `https://kagent.dev/extensions/hitl/v1` (header
`A2A-Extensions`) and replies with a `tool_approval_response`. kagent also serves its Sessions over
MCP, so Claude Code can talk to the same agent:

```sh
kubectl port-forward -n kagent svc/kagent-controller 8083:8083
curl -s http://localhost:8083/agents/kagent/turf/.well-known/agent-card.json   # the A2A agent card
claude mcp add --transport http kagent http://localhost:8083/mcp               # Sessions, over MCP
```

## Things to know

- **The token crosses the cluster network in cleartext**, from the egress gateway to the server over
  `http://`. Serve the server over TLS, or run a mesh, where that matters.
- **The server can read every Secret in `kagent-tfstate`**, so keep nothing else there
  ([Credentials in a cluster](/docs/cluster/credentials/#the-state-backend-and-variables-the-server)).
  The namespace is named in three places that must agree: `namespace.yaml`, the Role in
  `mcp-server.yaml`, and `backend_config.namespace` in the agent's prompt.
- **The engine's AWS key is the demo's**: a long-lived key for Lambda functions and IAM roles named
  `turf-kagent-*`. Widen the policy in `setup/aws` to what your configurations declare. Where the
  cluster has a cloud identity, give the engine's ServiceAccount a role instead of a key.
- **Scale from zero has a cost.** Each new engine pod installs providers and modules the first time a
  step lands on it.
- **Versions.** kagent 1.0.0, Knative Serving 1.24.0 with Kourier, the Restate operator 3.2.0,
  restate-server 1.8.1 and Turf 1.4.0, on kind with Kubernetes 1.37.0.

## Clean up

The fleets are in AWS, not in the cluster. Tear the stacks down first (ask the agent, and approve each
destroy), then delete the cluster, then the engine's IAM user and key:

```sh
kind delete cluster --name turf-kagent
turf -C setup/aws destroy
```

Lambda leaves a CloudWatch log group, `/aws/lambda/<function>`, for every function that was called.
The configuration does not declare them, so remove them by hand for a clean account.

## What runs where

| Namespace | What |
|---|---|
| `kagent` | the controller and UI; the WorkerPool the agent's sandbox runs on; the agent's `Harness`, `AgentTemplate` and `Agent`; a `ModelConfig` for Anthropic; `RemoteMCPServer`s for Turf and the OpenTofu Registry; the `EgressPolicy` |
| `ate-system` | Agent Substrate's control plane, and the egress gateway every connection from the sandbox goes through |
| `turf` | restate-server, the MCP server, the engine, the console, and their Secrets |
| `kagent-tfstate` | the state of the agent's stacks and nothing else: a Secret and a Lease per stack |
| `knative-serving`, `kourier-system` | Knative Serving and its Kourier gateway |
| `restate-operator` | the Restate operator |

The repository's [README](https://github.com/turfbuild/turf-kagent#readme) is the full reference: every
control between the parts, a check for each, and the rest of the notes.
