Turf™ runs in two processes, and each reads its own environment. Put a credential where the process
that uses it can see it.

- **Providers** run in the engine. They read the engine's environment, never your shell's.
- **Variables, the state backend and state encryption** are handled by the MCP server. They read the
  server's environment and the values your agent passes to `open` and each plan command.
- **Provider arguments** in the configuration (`profile`, `assume_role`, `config_path`) override the
  environment a provider would otherwise read.

A variable you `export` in a terminal reaches the server only when you start your agent, or the Turf
CLI, from that terminal. It never reaches the engine.

## Three processes, three views

```text
your shell
  │  you start your agent, or the Turf CLI, from it
  ▼
your agent ───── starts ─────►  MCP server  (turf-mcp-server)
                                environment: what your agent was started with,
                                  plus the env block of its MCP config
                                reads there: TF_VAR_*, backend credentials,
                                  TF_ENCRYPTION, TF_TOKEN_*, ~/.tofurc
                                handles: variables, the state backend,
                                  state encryption, init's installs
                                    │
                                    │  plans and applies: variable values
                                    │  travel; the server's environment stays
                                    ▼
                                engine  (turf-engine)
                                environment: its own (the turf service's:
                                  launchd, Homebrew's PATH, turf.env),
                                  then the configuration's mise environment
                                runs: the providers, which read it,
                                  and ~/.aws/config, ~/.kube/config
```

A `TF_VAR_` value reaches a provider only through a variable its block references. `TF_ENCRYPTION`
never leaves the server.

## Who reads what

| What | Read by | From |
|---|---|---|
| **Providers** (AWS, Azure, Google Cloud, Kubernetes®, …) | the engine | the engine's own environment, with the configuration directory's mise environment applied over it |
| **Variables, the state backend, state encryption** | the MCP server | the tool calls (`open`'s values, kept for the workspace, under each plan command's own) and the server's environment, set in your MCP client's `env` block; never mise |
| **Provider arguments** in HCL (`profile`, `assume_role`, `config_path`) | the configuration | override both: the way to pin an account in the configuration itself; a secret there arrives through a variable, never a literal |

## Where to set each one

- [The engine's environment](/docs/environment/engine-environment/): the `turf` service, `turf.env`,
  an engine in a terminal or in a cluster.
- [Per-configuration environment with mise](/docs/environment/mise/): an AWS profile, a kubeconfig
  path or a tool for one configuration only.
- [Variables and TF_VAR_](/docs/environment/variables/): values for `open` and each plan command.
- [State backend, registries and mirrors](/docs/environment/registries-and-mirrors/): backend
  credentials, `turf login`, provider mirrors.
- [State encryption](/docs/environment/state-encryption/): the OpenTofu™ `encryption` block and its
  passphrase.
