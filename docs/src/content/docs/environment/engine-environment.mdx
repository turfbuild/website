Providers run in the engine, so the environment they see is the engine's. Where a credential goes
depends on how the engine runs: started by the server on demand, as the `turf` Homebrew service, in a
terminal, or as a deployment of your own. `turf-mcp-server engine status` says which.

## An engine the server started

By default the server starts the engine when a tool first needs it. That engine has a small fixed
environment, the same whichever agent or shell the server came from:

- `HOME`, `USER`, `LOGNAME`, `SHELL` and `TMPDIR`;
- the `TURF_*` settings, `DO_NOT_TRACK` and `CI`, from the server's environment;
- `TF_PLUGIN_CACHE_DIR` and `TF_CLI_CONFIG_FILE`, from the server's environment;
- a `PATH` of Homebrew's and the system's directories.

Nothing else of your session reaches it. An `AWS_PROFILE` in your shell, or in the `env` block of
your MCP client's entry, reaches the server and the state backend, not the providers. Give providers
what they need in one of these ways:

- **Credential files.** The default profile in `~/.aws/config`, `~/.kube/config`, gcloud's
  application-default credentials and the `az` login are read as anywhere.
- **The configuration's mise environment.** Put a variable a provider needs, such as `AWS_PROFILE`,
  in the configuration's `mise.local.toml`: see
  [Per-configuration environment with mise](/docs/environment/mise/).
- **Provider arguments** in the configuration, [below](#provider-arguments-win).

For anything more, such as a proxy, run the Homebrew service and use `turf.env`.

## The Homebrew service

`brew services start turf` runs the same engine from login, and takes over one a server started. The
service runs the engine with launchd's environment on a Mac, Homebrew's `PATH`,
and what `~/.homebrew/services/turf.env` sets. It does not see your shell's environment. Put what
your providers need in `turf.env`, one `KEY=value` per line:

```sh title="~/.homebrew/services/turf.env"
AWS_PROFILE=platform-admin
ARM_SUBSCRIPTION_ID=00000000-0000-0000-0000-000000000000
```

Then restart the service:

```sh
brew services restart turf
```

A run paused at a plan gate or an approval point waits through the restart.

`turf.env` holds the service's other settings too: `TURF_MISE=off` turns off
[mise](/docs/environment/mise/), and `TURF_CONSOLE_ADDR`, `DO_NOT_TRACK` and `TURF_ACCEPT_EULA` are
read there, not in your shell. An engine the server started takes the same settings from the server's
environment, the `env` block of your MCP client's entry.

<Aside type="caution" title="A PATH in turf.env replaces the service's">
Follow your own directories with Homebrew's `bin` and the system directories, or the engine loses
the tools Homebrew's `PATH` gave it.
</Aside>

## An engine in a terminal

To watch the engine work, run it in the foreground:

```sh
export AWS_PROFILE=platform-admin
turf-mcp-server engine run
```

It has that terminal's environment, and runs until you interrupt it.

## A remote engine

When `TURF_RESTATE_URL` points the server at an engine you run yourself, the engine has whatever its
deployment gives it. In a Kubernetes® cluster that is the engine pod's environment: Secrets, through
`env` or `envFrom`. See [Credentials in a cluster](/docs/cluster/credentials/).

## License acceptance

The engine starts once the license terms are accepted, and where it looks follows the same rule as
everything else on this page: its own environment, never your shell's.

- **An engine the server started** is accepted as the server is: by the record
  `turf license accept` or `turf-mcp-server license accept` writes, `~/.turf/license.json`, or by
  `TURF_ACCEPT_EULA=yes` in the server's environment. The server starts no engine before that.
- **The Homebrew service** reads the same record. It
  waits for it, checking every 2 seconds, and starts the engine within seconds, with no restart.
  `TURF_ACCEPT_EULA=yes` in `turf.env` accepts too, after a restart of the service. The same variable
  in your shell, or in your MCP client's configuration, does not reach the service.
- **An engine in a terminal** reads the same record, or `TURF_ACCEPT_EULA=yes` in that terminal.
- **A remote engine** reads only its own environment, or its `--accept-eula` flag. In a pod that is
  an `env` entry: see [Minimal manifests](/docs/cluster/manifests/#the-license).

Setting `TURF_ACCEPT_EULA=yes` accepts the terms at `https://turf.build/license/v1/`. Until the terms
are accepted, `turf-mcp-server engine status` says `awaiting license`. More in
[Accept the license](/docs/start/install/#accept-the-license).

## Credential files

Credentials in their usual files are read in the engine as anywhere: the default profile in
`~/.aws/config`, `~/.kube/config`. The local engine is this user's, so it reads your files.
A remote engine reads its own.

Provider plugins run with the configuration directory as their working directory. A relative path a
provider resolves, such as a kubeconfig it writes, lands there, as with Terraform® run from that
directory.

## Provider arguments win

Arguments in a provider block (`profile`, `assume_role`, `config_path`) override the environment.
They are the way to pin an account in the configuration itself:

```hcl title="providers.tf"
provider "aws" {
  profile = "staging"
  region  = var.region
}
```

A secret in a provider block arrives through a variable, never a literal. With the credentials in
the engine's environment, a default provider instance needs no block at all; aliased instances need
their own blocks for what differs.

## Check what the engine runs with

```sh
turf-mcp-server engine status
```

With the npx install, `npx -y @turfbuild/turf-mcp-server engine status`. It says where the engine
runs, how it was started and whether it answers, the mise it found (or `off`), and where its logs
are:

```text
directory       /Users/you/.turf/engine
…
mise            /usr/local/bin/mise (2025.11.10 macos-x64 (2025-11-27))
logs            /Users/you/.turf/engine/restate.log
                /Users/you/.turf/engine/engine.log
```

If the engine does not come up, the reason is in `engine.log`, or in `supervisor.log` beside it for
an engine the server started.

## Common variable names

| Provider | Environment variables |
|---|---|
| AWS | `AWS_PROFILE`, `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` |
| Azure | `ARM_SUBSCRIPTION_ID`, `ARM_CLIENT_ID`, `ARM_CLIENT_SECRET`, `ARM_TENANT_ID` |
| Google Cloud | `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_PROJECT` |
