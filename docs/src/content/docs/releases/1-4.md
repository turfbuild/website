Release date to follow.

Turf™ 1.4 ships the console: a read-only web view of every workspace's runs, rounds and
approvals, running beside the engine. Every result the MCP server hands an agent now carries a
link into it, so when the agent says "the plan is ready", there is a page to look at: the round,
its plan, who approved what and when, and every resource's lane as the apply runs.

1.4 is built on OpenTofu™ 1.12.9 and tested on restate-server 1.8.1. It is a minor release:
upgrading restarts the engine and stops any 1.3 rollout still waiting for approval, so read
"Before you upgrade" first.

## What's new

**The console.** `brew services restart turf`, then `http://127.0.0.1:8873`. A workspace opens on
its runs, newest first, each opened into its rounds: what each round is doing or how it
ended, the plan's size, its approval point and who gave it, how long it took. A round's page
tells its story from the engine's own stamps: the plan gate while it is open, the plan with its
counts by action, the approval point with the approver and the plan's digest, the apply, any
turf action the apply is asking, and how the round ended the run. The Timeline tab draws
every resource's lane as the apply runs, live; Plan and Graph show one round's plan and
configuration graph; State shows what the workspace holds, its outputs and every address, each
opening to its committed record. It is read-only:
approvals are given where they always were, by the agent or the CLI. And only you can open it:
`turf console` signs your browser in once, and every link opens directly after that.

**A link in every result.** Every `up`, `plan`, `apply`, `status` and `open` result carries
`console_url`, the page for the round it is about, and the result's note asks the agent to give
you that link. `turf up` in the terminal shows it beside each gate. Set `TURF_CONSOLE_ADDR` to
move the console (`off` turns it off), or `TURF_CONSOLE_URL` on a server whose console lives
elsewhere, such as a cluster.

**The console in a cluster.** `turf-ui` ships in the `turf-mcp-server` image. Off loopback it
takes a token (`TURF_CONSOLE_AUTH_TOKEN`): a browser signs in once at `/login?token=…` and keeps
a cookie, a program sends it as a bearer header, and nothing else is answered. The kagent example
in turfbuild/turf-kagent runs it behind a port-forward, and the agent's message above an
approval card links to the plan the card is about.

**Planfiles and approvers in the history.** A workspace's planfiles, and each round's approver
and plan digest, are kept with the round history, so the console (and `status`) can say who
approved a round after its run's own record has expired.

## Before you upgrade

- **The console takes port 8873 on the laptop.** The Homebrew service starts it beside the
  engine; `TURF_CONSOLE_ADDR=127.0.0.1:<port>` moves it, `TURF_CONSOLE_ADDR=off` leaves it out.
  Run `turf console` once to sign your browser in.
  The engine does not depend on it: if the console stops, the engine goes on.
- **The Turf CLI and `turf-mcp-server` must be the same release**, as in 1.3.

## Upgrading from 1.3

```sh
brew upgrade turfbuild/tap/turf
brew services restart turf
```

Then restart your agent's MCP connection. As in 1.3, the restart stops every rollout still on
the 1.3 engine: one waiting for approval ends `cancelled` with the upgrade as the cause, and one
in the middle of an apply finishes what is in flight and ends `partial`. Everything applied is
kept: run `up` again, and `plan` plans what remains.

**In a cluster**, replace every 1.3 replica before a 1.4 replica serves, and add the console's
Deployment and its token Secret (the turf-kagent manifests show both).
