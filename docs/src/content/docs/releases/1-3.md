Released 2026-11-02.

Turf™ 1.3 gives each step of a rollout its own tool: `up` starts it, `plan` plans each round, and `apply` applies the plan you approved. You choose each round's options when you reach it, and an agent never holds a call open for minutes. A plan can be made on one server and applied on another, with different credentials. Configurations can call provider-defined functions, and the HTTP endpoint can require a bearer token.

1.3 is built on OpenTofu™ 1.12.9 and tested on restate-server 1.8.1. It is a minor release: upgrading stops any 1.2 rollout still waiting for approval, and agents, skills and prompts written for 1.2 need the new `plan` step, so read "Before you upgrade" first.

## What's new

**Plan each round with `plan`.** A rollout now stops twice every round: at its plan gate, before anything is planned, and at its approval point, with the plan. `up` (and `destroy`, `refresh`, `import`, `invoke`) starts the rollout and stops at round 1's plan gate. `plan` plans the round with that round's options: `refresh: false` to plan against the state as recorded, `replace` to force a replacement. `apply` with the plan's digest applies it and stops at the next round's plan gate, or ends the rollout. Options belong to the round you give them to, so a `replace` no longer carries into round two. To turn a plan down, call `apply` with `decline` and a reason.

```text
up({})                                                  → awaiting_plan, round 1
plan({ convergence_id, replace: ["aws_instance.web"] })  → awaiting_approval, with the plan
apply({ convergence_id, plan_digest })                  → awaiting_plan, round 2 (or the end)
```

**Every call comes back within a minute.** Each `up`, `plan` and `apply` returns within the server's deadline (55 seconds, under the MCP clients' usual 60-second limit; `turf-mcp-server --deadline` changes it). A round that takes longer keeps running in the engine: the call says it is still `planning` or `applying`, and the agent calls again to follow it. The Turf CLI allows five minutes.

**Plan in one place, apply in another.** Start a rollout with `plan_only: true` and its `plan` ends the rollout `planned`: nothing is applied, the workspace is free, and the engine keeps the plan as a planfile for 24 hours. `apply({ workspace_alias, planfile, plan_digest })` applies it later, from the same server or from another one with its own credentials, after checking that the configuration, the state and the digest haven't moved since the plan. `show({ planfile })` reads it, and `status` lists the planfiles a workspace holds.

**Permission tiers.** `turf-mcp-server --tier read|plan|apply|full` (or `TURF_TIER`) gives a server only that tier's tools. A plan-tier server plans and can't apply: every rollout it starts is plan-only. An apply-tier server applies planfiles and can't start a rollout. Give the planner and the applier different credentials, and neither can do the other's job. `full`, the default, is everything.

**Provider-defined functions.** `provider::<name>::<function>(…)` works wherever an expression does, as in Terraform®, for a provider's own functions and the built-in `terraform` provider's:

```hcl
locals {
  expires = provider::time::rfc3339_parse(var.expiry).unix
}
```

Each module declares the providers it calls. `provider_describe` takes `function` to describe one: its parameters, return type and description.

**A bearer token for the HTTP endpoint.** Set `TURF_MCP_AUTH_TOKEN` and `turf-mcp-server --transport http` refuses any request without `Authorization: Bearer <token>`, with a `401`. Use it when something other than your MCP client can reach the port, such as an agent's own container in CI: with a token only the client holds, the agent can't call the server directly and skip the client's tool list. The token comes from the environment only, and stdio ignores it.

## What's fixed

- **Under CI, the engine sends no installation id unless `TURF_INSTALLATION_ID` gives it one.** Before, every fresh CI runner minted a new id. Set `TURF_INSTALLATION_ID` to count your pipelines as one installation; `TURF_TELEMETRY=off` still turns telemetry off.
- **`turf telemetry on|off` no longer mints an installation id.** The engine's service is the only thing that does.
- **The CLI's feedback links point at Turf's own channels.**

## Before you upgrade

- **Agents, skills and prompts written for 1.2 need the `plan` step.** `up` no longer plans: it stops at the plan gate, and `plan` makes the plan. `auto_approve` is gone, and `refresh` and `replace` moved from `up` to `plan`. A start given `auto_approve: true`, `refresh: false` or a `replace` is refused with a message saying where it went, so nothing is skipped silently. The server's own instructions and skills already describe the new loop.
- **If your MCP client lists the tools it allows, add `plan`**: a kagent agent's `toolNames`, a GitHub agentic workflow's `allowed:` list, a Claude Code `--allowedTools`. Without it the agent stops at the first plan gate.
- **`turf up --yes` approves nothing up front.** It answers the agent's confirmations yes for you as each round's plan comes, a destroy's included, so a run still goes through every round.
- **The Turf CLI and `turf-mcp-server` must be the same release.** The 1.3 CLI starts the server with `--deadline 5m`, which a 1.2 server rejects at start.

## Upgrading from 1.2

```sh
brew upgrade turfbuild/tap/turf
brew services restart turf
```

Then restart your agent's MCP connection too, because a 1.2 server can't talk to the 1.3 engine.

1.3 runs its own engine beside 1.2's. At the restart, every rollout still on the 1.2 engine is stopped. One waiting for approval or for a turf action ends as `cancelled`, with the upgrade named as the cause, and one in the middle of an apply finishes what is in flight and ends `partial`. Everything already applied is kept: run `up` again, and `plan` plans what remains. The 1.2 engine goes away as soon as nothing is left on it, usually within a minute, and `turf-mcp-server engine status` shows it while it drains.

**In a cluster**, replace every 1.2 replica before a 1.3 replica serves. If your MCP client has a call timeout under a minute, set `--deadline` below it: the kagent example in turfbuild/turf-examples runs the server with `--deadline 25s`, under kagent's 30-second timeout.

## Install

```sh
brew install restatedev/tap/restate-server turfbuild/tap/turf
brew services start turf
```

Then connect your agent:

```sh
npx add-mcp@2 "$(command -v turf-mcp-server)" --name turf -g
# or, for Claude Code:  claude mcp add turf --scope user -- turf-mcp-server
```

Or use the Turf CLI with your own model API key: `turf -C ./path/to/config up`.

Each tarball carries four binaries, `turf`, `turf-mcp-server`, `turf-engine` and `turf-builtin-provider`, which go on your `PATH` side by side. Setup for each agent: https://github.com/turfbuild#connect-your-agent.

## Container image
```sh
docker pull ghcr.io/turfbuild/turf-mcp-server:v1.3.0   # also :latest
```

## Verify your download

```bash
ID='^https://github.com/turfbuild/turf-mcp-server/'
ISS=https://token.actions.githubusercontent.com

# CLI — provenance + SBOM
gh attestation verify turf --repo turfbuild/turf

# Server binary — cosign (bundle ships on this release);
# turf-engine and turf-builtin-provider verify the same way, with their own bundles
cosign verify-blob-attestation --type slsaprovenance1 \
  --bundle turf-mcp-server-<os>_<arch>.provenance.sigstore.json \
  --certificate-identity-regexp "$ID" --certificate-oidc-issuer "$ISS" \
  turf-mcp-server-<os>_<arch>

# Container image
cosign verify ghcr.io/turfbuild/turf-mcp-server:v1.3.0 \
  --certificate-identity-regexp "$ID" --certificate-oidc-issuer "$ISS"
```

`checksums.txt` is the no-tooling fallback.
