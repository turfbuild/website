Turf™ is software you run inside your own system boundary. It holds no authorization of its own, and
your system's controls remain yours to implement and assess. This page shows which NIST SP 800-53
Rev. 5 controls Turf helps you meet, where each capability is documented, and what Turf leaves to you.

Use it as input to a system security plan: each row names a control, what Turf contributes, and the
page that describes it.

## Configuration management (CM)

| Control | What Turf contributes | Documented in |
|---|---|---|
| CM-2 Baseline configuration | The desired state is a configuration of ordinary Terraform® files, and every plan is made from it. | [What Turf is](/docs/start/what-turf-is/) |
| CM-3 Configuration change control | Every change is a plan that waits at an approval point. An approval names the plan's digest and applies that plan only; if the configuration changes before the apply, the run ends `stale` and nothing is applied. | [Approval](/docs/concepts/approval/) |
| CM-4 Impact analyses | A plan waits at its approval point, and nothing applies until its digest is named. Policy tools read that exact plan as a JSON document before the approval. | [Policy checks on a plan](/docs/using/policy/) |
| CM-5 Access restrictions for change | A server's tier decides what its credential can do: read, plan, apply or everything. | [Tiers](/docs/reference/server/#tiers) |
| CM-8 System component inventory | Each release ships a software bill of materials in CycloneDX and SPDX. | [Verify a release](/docs/security/verify-releases/#bills-of-materials) |
| CM-14 Signed components | Every binary and the container image are signed, and the installer verifies them with `--verify`. | [Verify a release](/docs/security/verify-releases/) |

## Access control and identification (AC, IA)

| Control | What Turf contributes | Documented in |
|---|---|---|
| AC-3 Access enforcement | With `TURF_MCP_AUTH_TOKEN` set, the MCP server over HTTP refuses any request without its bearer token. Off loopback, the console answers no read without its token. | [Topology](/docs/cluster/topology/#the-mcp-server), [The console](/docs/cluster/console/#sign-in) |
| AC-5 Separation of duties | A plan-tier server plans and seals each plan as a planfile. An apply-tier server, with its own credentials, applies it by digest. | [Planfiles](/docs/using/planfiles/) |
| AC-6 Least privilege | The server never runs a provider, so provider credentials go on the engine alone. Each ServiceAccount gets only what its piece needs, and the console's gets nothing. | [Credentials in a cluster](/docs/cluster/credentials/#rbac-at-a-glance) |
| IA-5 Authenticator management | Provider credentials belong in the engine's environment and backend credentials in `open`'s `backend_config`, not in the configuration. A stored plan records an ephemeral variable by name only. | [Variables](/docs/authoring/variables/#secrets) |
| IA-9 Service identification and authentication | restate-server signs every request it sends the engine, and the engine serves nothing unsigned. | [Credentials in a cluster](/docs/cluster/credentials/#the-identity-key-restate-server-and-the-engine) |

## Audit and accountability (AU)

| Control | What Turf contributes | Documented in |
|---|---|---|
| AU-2, AU-12 Event logging, audit record generation | The engine records every run and each of its rounds as it happens: the plan, the approval, the apply and how it ended. | [The engine and the console](/docs/concepts/engine-and-console/) |
| AU-3 Content of audit records | A round's page shows the plan with its counts by action, the plan's digest, the approver, each resource's lane through the apply, and how long the round took. | [The console](/docs/cli/console/) |
| AU-9 Protection of audit information | The console is read-only. Nothing in it changes a record. | [The console](/docs/cluster/console/) |

| Control | What Turf contributes | Documented in |
|---|---|---|

| Control | What Turf contributes | Documented in |
|---|---|---|

| Control | What Turf contributes | Documented in |
|---|---|---|
| SI-2 Flaw remediation | Each release is scanned before it is tagged. A release carries the disposition of every known vulnerability in a dependency. | [Verify a release](/docs/security/verify-releases/#vulnerability-disposition) |

## What Turf leaves to you

Plan for these when you write your controls:

- **People are identified by your platform, not by Turf.** Turf authenticates a server and a console
  with one token each. It has no user accounts and no single sign-on. The approver in a round's
  record is the name the client gave. Identify people in your agent platform and at the network edge
  (AC-2, IA-2).
- **Encrypt the engine's store.** The engine's records and plan documents are plaintext in
  restate-server's store, including the values of sensitive variables. Put the store on an encrypted
  volume and restrict who can read it (SC-28).
- **Protect the token in transit.** The MCP server does not serve TLS itself. Serve it behind TLS or a
  service mesh, or keep the network path private (SC-8).
- **Keep audit records as long as you need them.** The engine keeps a run's record for its own
  retention period and does not export it. Collect the engine's and the server's logs, and the
  round history you need, into your own log system (AU-4, AU-11).
- **Providers are separate programs.** Each provider calls its own API with the credentials you give
  the engine. Review providers as you would any component, and pin them with the lock file.
- **Your model is outside Turf.** Turf does not call a model. What your agent sends to its model is
  governed by the agent platform you choose.
